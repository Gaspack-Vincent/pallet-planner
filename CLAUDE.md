# Pallet Planner (Salco)

Internal tool for Salco bv that plans how aluminum profiles are packed onto pallets. Single-page app, Dutch UI, no build step — open `index.html` directly or serve statically.

## Files
- `index.html` — markup/UI shell
- `app.js` — all application logic (~3200 lines)
- `styles.css` — styling
- `fonts.css` — embedded/base64 font-face declarations (large file)
- `lib/xlsx.js` — vendored SheetJS, used for Excel import/export

These were split out of a single large `index.html` export (originally saved from `index_13.html`) so the code is easier to work on. Keep the split: don't re-inline JS/CSS into `index.html`.

## Key flows in `app.js`
- **Profile database** (`DB` object, top of file): article number → profile (length, weight, category, class). Hardcoded, ~60 entries, not meant to be hand-edited at runtime.
- **DB overrides** (Supabase `db_overrides` table, shared across users): edits/renames/deprecations layered on top of `DB`. `dbRecFor(art)` / `dbLookup(artRaw)` are the only places that should resolve "what do we know about article X" — they merge override > `DB` > `_customDB` (never read `DB[...]` directly elsewhere). `art_nieuw` on an override represents a rename (old key stays the Supabase row's PK; `art_nieuw` is the number shown/searched going forward, resolved via `dbRenameFromMap()`). `vervallen: true` hides an article from the VAST tab and the "artikel toevoegen" picker without deleting its data (`allVastArtKeys()` = `DB` keys ∪ override keys, so brand-new shared articles show up too). `bron` ('bewerk' vs 'import') tracks *why* the override exists — only 'bewerk' (a manual save via the "Bewerken" form) shows the AANGEPAST badge + Herstel button in the VAST tab; a bulk Excel import is meant as a silent replacement of the source data, not a flagged edit. `bron` is sticky: an import re-touching an article that was already manually edited keeps 'bewerk' rather than downgrading it (see `dbOvImportExcel`).
- **Custom DB** (`_customDB`, browser-local via `localStorage`, key `salco_custom_artikeldb`): per-browser scratch articles, NOT shared. Still used by the "EIGEN" tab's manual add-form and delete (`cdbToevoegen`/`cdbVerwijderen`). There is deliberately no Excel-import into `_customDB` anymore — bulk imports always go through `dbOvImportExcel` → `db_overrides` (shared), since that's what's actually used in practice.
- **Shared Excel import/export** (`dbOvImportExcel` / `dbOvExportExcel`): the import column-detection accepts *either* the app's generic header names (Artikelnummer/Omschrijving/Lengte_mm/Gewicht_kg) *or* Salco's own material-master format (Materiaalnummer/Omschrijving/Afmeting/"Gewicht per /st.", as in `Profielen bestand.xlsx`) — same file, same headers, no conversion needed. Watch the disambiguation logic: "Afmeting" (mm) must win over "Standaardafmeting" (m), and "Gewicht per /st." (per piece) must win over "Gewicht per /m" — both resolved via exact-match-first column lookup. Rows are deduped by article number client-side (last row wins) before the bulk upsert, since a single Postgres statement can't `ON CONFLICT` the same key twice. The source file's opaque "Pallet" column (a standard pallet-length lookup unrelated to this app's own long/short bucketing) is stored verbatim as `pallet_len` and reproduced as-is on export — never computed/guessed, since its business rule isn't derivable from length/weight alone.
- **Profile photos** (Supabase Storage bucket `profielfotos`, public): looked up by article number as filename (`{art}.jpg`/`.png`/`.jpeg`). No DB field for this — pure filename convention. Every pallet item row renders an always-visible thumbnail via `profielFotoThumbHtml(art)` (silently omitted if no photo exists in any extension); clicking it opens a full-size lightbox (`toonProfielFotoGroot`/`sluitProfielFotoGroot`, `#pr-foto-modal` in `index.html`). `window._prFotoCache` remembers which extension worked (or `false` for "no photo") per article so re-renders (very frequent in this edit-heavy UI) don't re-probe all three extensions every time.
- **Import**: `processFile` / `parseBrowsom` parse an uploaded order file.
- **Planning**: `runPlanning` → `computePlan` → `packItems` — the core bin-packing logic that assigns profiles to pallets under weight/space limits.
- **Results & export**: `showResults`, `exportExcel` (via `lib/xlsx.js`). `renderSummarySidebar()` (fills `#summaryArea`) is factored out of `showResults()` so per-pallet edits that only affect the sidebar (see next point) don't have to re-render every pallet card and blow away input focus.
- **Werkelijke maat/gewicht** (`pal.werkelijkL`/`werkelijkB`/`werkelijkH`/`werkelijkKg`, plain fields on each `plan[i]` pallet object, persisted via `saveCurrentProject`): optional post-packing documentation, filled in via `phWerkelijkHtml()` under each pallet's weight bar (L/B/H as three side-by-side number inputs, weight as a fourth). Pure documentation — never feeds back into planning/packing logic (`packItems`, `MAX_P`/`MAX_S` checks, `overloaded`/`stackViolation`) or the per-pallet weight bar itself; only changes *display*: the summary sidebar's per-pallet row (L/B/H columns left of the weight column, mirroring the export) and its "Totaal kg" prefer `werkelijkKg` over the estimated `totalKg` when present (`renderSummarySidebar()`), and it's saved to `projects.total_kg` the same way. `exportGewichtenlijst()` exports these in the exact cell layout of Salco's own reference file ("Voorbeeld export (.xlsx) gewichtenlijst.xlsx": column A empty, project number in B2/C2, headers in row 4, one row per pallet), followed by one row per krat, plus one extra column H "Type" ('X-pallet' when `pal.x`, 'Normaal', or 'Krat') that isn't in the reference file — falls back to the estimated `totalKg` per pallet when no `werkelijkKg` was entered yet, so the export always has a weight even mid-packing.
- **Kratten** (`kratten` state array of `{maat,l,b,h,kg}`, separate from `plan`): loose crates in the shipment, pure documentation like the werkelijke maat fields — no profile distribution, never touches `plan`/packing. Added in bewerkmode via the same "Pallet / krat toevoegen" picker as pallets (step 1 Pallet/Krat via `toonAddStap`, then `voegPalletToe` or `voegKratToe(maat)`); `KRAT_MATEN` holds the two standard sizes (Small 1140×750×1260, Medium 2290×750×1260), prefilled into l/b/h on add, weight starts empty. Rendered by `kratSectieHtml()` as a "Kratten" section below the stapels in `#palletResults`, with cards using their own `.kc/.kh/.kb` classes — deliberately *not* `.pc/.ph/.pb`, because `activeerBewerkmode()` hooks pallet drag-drop and artikel-drop onto those. An "OK" button next to the weight (`kratKlaar(i)`, refuses without a weight) sets persisted `k.klaar` and renders the card compact like a `.pallet-done` pallet (`.kc.krat-done`, TOON → `toonKrat(i)` expands again); these only re-render the krat section itself (`renderKratSectie()`, `#krat-sectie`) so pallet state isn't disturbed. Field edits (`updateKrat`) only re-render the sidebar to keep input focus; add/delete re-render via `kratHerrenderInBewerkmode()`. Named via stored `k.nm`: on add it continues the NM numbering *across pallets and kratten together* (`volgendNmNummer()`, also used by `voegPalletToe`, so a pallet added after a krat doesn't reuse its number); in bewerkmode the name is an editable input (`updateKratNaam`, rejects empty or duplicate names). `kratNaam(k,i)` falls back to "Krat n" for kratten without `nm`. Kratten are counted in the summary sidebar, its "Totaal kg" and `projects.total_kg` (`krattenKg()`), and exported as extra rows (Type "Krat Small"/"Krat Medium") in `exportGewichtenlijst()`. Persisted in Supabase column `projects.kratten` (jsonb); `saveCurrentProject` only sends that field when there are kratten or a loaded project proved the column exists (`krattenKolomBestaat`), so saving doesn't break on a database without the column.
- **Projects (Supabase-backed, shared across users)**: `sbGet`/`sbUpsert`/`sbDelete`, `saveCurrentProject`, `loadProject`, `deleteProject`.
- **DB browser** (this is the *projects* list, not the profile `DB` — naming collision, be careful): `renderDB`, `filterDB`, `renderDBRows`, `cycleStatus`.

## Backend
Supabase project at `gahqjogmbofdonsxenph.supabase.co`. The embedded `SB_KEY` in `app.js` is the public **anon** key (safe to expose client-side; access is governed by Supabase row-level security, not this key). Tables: `projects`, `containers`, `db_overrides` (see above). Storage bucket: `profielfotos` (public).

## Known gotchas
- **`pal.profW` must always equal `pal.items.reduce((s,i)=>s+i.gew,0)`.** Every bewerkmode mutation (`verplaatsItem`, `bewerkQtyChange`, `bewerkOpslaanInline`, `verwijderArtikel`, `bevestigArtikelToevoegen`, `voegArtikelToe`) recomputes `profW` this way rather than nudging it with `+=`/`-=` deltas — a same-pallet drag-reorder in `verplaatsItem` used to unconditionally subtract the moved item's weight without ever adding it back, silently corrupting the pallet's shown weight. If you add a new way to mutate `pal.items`, recompute `profW` from `items` afterward instead of tracking a delta. The one-shot bin-packing algorithm (`computePlan`/`packItems`, incl. `addItem()`) is exempt — it only ever adds, in one linear pass, so no drift risk there.

## Conventions
- Dutch variable/comment names throughout — match existing style rather than switching to English.
- No package manager / bundler — plain `<script>` tags, so any new dependency must be vendored into `lib/` like `xlsx.js`.
